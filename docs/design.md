# Internet Archive MCP Server — Design

## MCP Surface

### Tools

| Name | Description | Key Inputs | Annotations |
|:-----|:------------|:-----------|:------------|
| `ia_find_snapshots` | Find Wayback Machine snapshots of a URL. Mode `closest` returns the single nearest capture to a given timestamp, or the latest capture when `timestamp` is omitted, via the Availability API, falling back to a CDX closest-capture query when the Availability API finds no capture or answers with a rate limit, a server error, an unreadable response, or an `error` in place of a capture. A Wayback capture URL as `url` reads as the URL it archives. Mode `history` returns the full capture list via CDX — filterable by date range and HTTP status, collapsed by default to one capture per day; `collapse` `digest` lists each content change and `urlkey` one row per URL, and a `url` ending in `*` lists every URL under that prefix. Timestamps take 1–14 digits or an ISO 8601 date or UTC date-time. Returns timestamps and `https://web.archive.org` replay URLs. At most 10,000 records per call — a larger `limit` is served as 10,000 with a notice naming `resume_key` — and resume-key pagination for large histories. A history query that no capture matches returns an empty list and a notice saying why. | `url`, `mode` (`closest`\|`history`), `timestamp` (closest mode), `from`/`to`, `status_filter`, `limit`, `collapse` (`timestamp:N` precision, `digest`, or `urlkey`; default `timestamp:8`), `resume_key` (history mode) | `readOnlyHint: true`, `idempotentHint: true`, `openWorldHint: true` |
| `ia_get_snapshot` | Fetch the archived content of a URL at a specific Wayback timestamp, or of the capture a Wayback capture URL such as a `replay_url` names. Resolves to the nearest available capture when the exact timestamp has no snapshot. Returns the archived text content (an HTML page stripped to readable text in lines, its table cells separated by tabs, another text type as stored; a non-text capture fails as `non_text_capture`) one page at a time, with the replay URL and timestamp of the capture Wayback served. With `include_links`, also the page's links as text and URL. A blank `timestamp` reads the timestamp of a Wayback capture URL passed as `url`, else the latest capture. | `url`, `timestamp`, `char_offset`, `max_chars`, `include_links` | `readOnlyHint: true`, `idempotentHint: true`, `openWorldHint: true` |
| `ia_search_items` | Search the Internet Archive library (40M+ items) via the Advanced Search / Solr API. Filter by media type, collection, creator (every word of the name, close together, in any order), publication date range (an item with no `date` never matches; an upload-time range goes in `query` as `publicdate:[…]`), and language (any code or name of a known language). Sort by downloads (the default), date, title, or random, with ties ordered by `identifier` except under random. Returns identifiers, titles, creators (the first 10, with `creator_count` when a record lists more), media types, publication dates, upload dates (`publicdate`), download counts, collections (without `fav-` favorites lists), `total_found`, and current `page`/applied `rows` for pagination context. At most 200 rows per call — a larger `rows` on page 1 is served as 200 with a continuation notice — within Advanced Search's 10,000-result window. | `query`, `mediatype`, `collection`, `creator`, `date_from`/`date_to`, `language`, `sort`, `rows`, `page` | `readOnlyHint: true`, `openWorldHint: true` |
| `ia_get_item` | Retrieve metadata and the file manifest for an Archive item by identifier. Returns title, creator, description (as plain text), the publication date, `publicdate` and `addeddate` (when the item was made public and when it was added), subjects, collections, license, language, publisher, volume, ISBN, OCLC and LCCN numbers, Open Library edition and work IDs, `runtime` (audio and video), `image_count` (texts), `access_restricted`, the full `file_count`, and a page of files (default 50, at most 500 per call — a larger `max_files` is served as 500) with format, size, and direct download URL (`private: true` on a file whose download is refused; for an audio or video file also `title`, `track`, and `length`), optionally filtered to one format. Every metadata field may be a string or a list. `identifier` also takes an archive.org item URL. The primary hub for acting on a search result. | `identifier`, `format`, `max_files`, `file_offset` | `readOnlyHint: true`, `idempotentHint: true`, `openWorldHint: true` |
| `ia_get_text` | Retrieve readable OCR DjVuTXT or plain text by identifier. Each call reads one text file: `file`, or by default the first DjVuTXT file, else Text, Plain Text, or another `.txt` file (Metadata sidecars excluded); an item with several such files gets a notice giving the count. `identifier` also takes an archive.org item URL. Page by UTF-16 offset or an expiring continuation token, or start at a phrase's first match (`find`, reported as `match_offset`); return `has_more`, source-file metadata, and the next token when available. | `identifier`, `file`, `max_chars`, `char_offset`, `continuation`, `find` | `readOnlyHint: true`, `idempotentHint: true`, `openWorldHint: true` |

A blank `query`, `identifier`, or `url` (empty or whitespace-only) never reaches a handler: the input schema rejects it as the framework's `invalid_arguments` (`InvalidParams`).

## Overview

Access the Internet Archive's two main pillars through a single MCP server:

1. **Wayback Machine** — historical snapshots of any URL, from a single "closest capture" lookup to the full multi-decade capture history via the CDX API.
2. **IA Library** — 40M+ items across texts, audio, video, software, and images, searchable by keyword and metadata, with per-item file manifests and text retrieval.

Target audience: researchers, journalists, fact-checkers, and any agent that needs to verify what a web page said at a past time or mine the open-source library. The Wayback tools compose broadly — "snapshot any URL an agent is about to cite" works alongside every other MCP server.

---

## Requirements

- Read-only access to all four APIs; no credentials needed
- Wayback Availability API: `GET archive.org/wayback/available?url=&timestamp=` — closest snapshot to a given time, single-result response; answers `archived_snapshots: {}` for some heavily archived URLs that have captures, and HTTP 200 with an `error` object (`{"code": "timeout", …}`) in place of a capture when its own lookup times out
- Wayback CDX API: `GET web.archive.org/cdx/search/cdx?url=&output=json` — full capture history; array-of-arrays with header row; supports field selection (`fl`), collapsing (`collapse`), date range (`from`/`to`), status filtering, resume-key pagination, and closest-first ordering (`closest=&sort=closest`)
- Advanced Search API: `GET archive.org/advancedsearch.php?q=&output=json` — Solr-based; `response.docs` envelope; supports `fl[]` field selection, `rows`, `page`, `sort[]`; reports a rejected request as HTTP 200 with `{"error": "…"}` and no `response`; serves no result past the 10,000th
- Metadata API: `GET archive.org/metadata/{identifier}` — returns `metadata` object + `files[]` array; `{}` on unknown identifier; `GET archive.org/metadata/{identifier}/files` returns `{"result": [...]}`, the record's `files` entries alone, and HTTP 200 with an `error` body for an unknown or a dark item
- Identifying User-Agent required as a courtesy per IA's terms
- Respect backoff on 429; CDX can time out on unbounded queries — always use `limit` and `collapse` defaults
- No DataCanvas — capture lists and search results are discovery metadata (timestamps/URLs/identifiers), not analytical rows

## Implementation Order

1. **Config** — `src/config/server-config.ts` with the three env vars above
2. **WaybackService** — Availability and CDX clients; `findClosest()`, `fetchHistory()`, `fetchContent()` methods
3. **ArchiveSearchService** — Solr search client; `search()` with field selection
4. **ArchiveMetadataService** — Metadata and download clients; `getItem()`, `getTextContent()`
5. **`ia_find_snapshots`** — both modes (closest + history)
6. **`ia_get_snapshot`** — snapshot content retrieval with text extraction
7. **`ia_search_items`** — library search
8. **`ia_get_item`** — item metadata + file manifest
9. **`ia_get_text`** — OCR text retrieval with pagination
10. **`ia://item/{identifier}` resource** — lightweight metadata injectable context

## Workflow Analysis

### `ia_find_snapshots` (mode: `history`)

| # | Call | Purpose |
|:--|:-----|:--------|
| — | Read a Wayback capture URL in `url` as its original URL; its timestamp is not read in history mode, though an impossible one still fails as `invalid_timestamp` | Local check, no request |
| — | Normalize `from` and `to` (1–14 digits or ISO 8601; a prefix starts or ends its period) and reject an invalid one; a reversed range passes through to CDX and answers an empty list with a notice | Local check, no request |
| 1 | `GET /cdx/search/cdx?url=&fl=timestamp,statuscode,mimetype,original,digest,length&collapse=timestamp:8&limit=N&showResumeKey=true` | For an exact URL under any `collapse` (`timestamp:N`, `digest`, `urlkey`), fetch the applied page size plus one row; a server cursor resumes inclusively at its saved next timestamp through `from`, and a resumed `digest` page asks for `limit + returned + 2` rows (see Design Decisions). A wildcard `url` or a key the server did not issue uses CDX's raw `resumeKey` |
| — | Require the body to be a list of rows of strings (anything else is `cdx_unavailable`); parse header row; strip it; map rows to objects | Local transform (no extra call) |
| — | Strip trailing `[]` or `[""]` separators and their key; expose a server cursor or raw key as `resume_key` | Exact-URL cursors keep the unreturned row for the next page; raw-key and wildcard continuation carries an incompleteness notice |
| — | With no rows, return `snapshots: []` and one notice saying why | See Design Decisions |

### `ia_get_snapshot` 

| # | Call | Purpose |
|:--|:-----|:--------|
| — | Read a Wayback capture URL in `url` as its original URL and timestamp; normalize `timestamp` (1–14 digits or ISO 8601) and reject an invalid one, or one that differs from the capture URL's | Local check, no request; a blank `timestamp` reads the capture URL's timestamp, else the latest capture |
| 1 | `GET /wayback/available?url=&timestamp=` | Resolve nearest snapshot URL (skipped for an exact 14-digit timestamp; `timestamp` omitted for the latest capture) |
| 1b | `GET /cdx/search/cdx?url=&closest=&sort=closest&limit=10&fl=timestamp,original,statuscode` | Only when step 1 has no usable answer (empty, 429, 408, 425, or 5xx after retries, an HTML or unparseable body, or an `error` body, which is not retried): nearest capture, preferring a `200` row; one attempt, under the least of 25 s, the request timeout, and the time left in the call's deadline |
| 2 | `GET web.archive.org/web/{resolved_timestamp}/{url}` | Fetch the replay with `redirect: 'manual'`; the service follows its redirects (up to 10, Wayback Machine hosts only) to the capture Wayback serves. The `Content-Type` decides the read: HTML (or none) is read here, another text type has this body cancelled unread, any other type fails as `non_text_capture` |
| 2b | `GET web.archive.org/web/{resolved_timestamp}id_/{url}` | Only for a non-HTML text capture: the body as stored, without Wayback's URL rewriting |
| — | Stream at most 4 MiB of the body (cancel the rest); decode with the declared or guessed charset; for HTML, remove markup and decode character references into lines (a block element or `<br>` starts a line, table cells are separated by tabs, `<pre>` is kept as written, other whitespace collapses; text-level tags add no separator, except one space between two words where a link and the element beside it meet; template content and hidden phrasing content are left out); with `include_links`, the same scan also collects each `<a href>` outside a template or hidden part and the first `<base href>`, and the page's links are those whose first occurrence starts in the page; slice the page at `char_offset` for `max_chars` and report `has_more` and `total_chars` | Local transform; links add no request |

### `ia_search_items`

| # | Call | Purpose |
|:--|:-----|:--------|
| — | Reject `rows` > 200 past page 1 and `page × rows` > 10,000; cap `rows` at 200 on page 1 | Local check, no request |
| — | Reject a `creator` or `language` with no letter or digit (`invalid_filter`) and a `query` ending in an unpaired backslash (`invalid_query`) | Local check, no request |
| — | With any filter, send `q` as `(<query>) AND <filters>`: `creator:"<name>"~N` with N = 2 × (words − 1), an exact phrase past 34 words; `language:(<spelling> OR …)` over every spelling of a known language, else `language:"<value>"` | Local transform |
| — | Trim date bounds, validate Gregorian dates, and expand year/month bounds to the period's first or last day | Local check, no request; omitted sides use `*`, and both omitted means no date filter |
| 1 | `GET /advancedsearch.php?q=&fl[]=...&rows=&page=&sort[]=&output=json` | Solr search with field projection (`fl[]` includes `publicdate`) |
| — | Classify an `error` body; drop `fav-` entries from `collection`; cut `creator` to 10 with `creator_count`; relay `publicdate` as received, omitted when absent | Local transform |

### `ia_get_item`

| # | Call | Purpose |
|:--|:-----|:--------|

## Design Decisions

**Two Wayback tools, not one.** `ia_find_snapshots` (discovery) and `ia_get_snapshot` (retrieval) separate the "what snapshots exist" workflow from the "show me what the page said" retrieval. Merging them conflates two distinct agent intents and would produce an awkward dual-mode shape. The `mode` parameter inside `ia_find_snapshots` is a good fit because both modes answer the same question ("what snapshots exist?") via different API paths — that's within-tool disambiguation, not two separate goals.

**CDX collapse default.** Popular URLs have tens of thousands of captures. Default `collapse=timestamp:8` (one per day) keeps responses tractable. The `collapse` parameter accepts `timestamp:N` (precision digits: 4=year, 6=month, 8=day, 10=hour, 14=second; CDX reads an N above 14 as 14 and `timestamp:0` as the first capture in range), `digest`, and `urlkey`, validated with `z.string().regex(/^(?:timestamp:\d{1,2}|digest|urlkey)$/)`; arbitrary strings are rejected. `digest` lists the first capture in range and each capture whose digest differs from the one before it, so a change back to earlier content is listed as a change, and answers "did the page change" without comparing rows by hand; `urlkey` lists one row per URL, its first capture in range, which on a `url` ending in `*` is one row per URL under the prefix. `status_filter` applies before the collapse, so `digest` with `status_filter: "200"` leaves out redirect captures, whose own digests otherwise list the page again after each one. An omitted or blank `collapse` is unset, per the blank-optional convention, so both send the `timestamp:8` default. `timestamp:14` is the finest listing — one row per distinct capture second (`example.com` in 2015: 364 rows at the default, the 10,000 cap at `timestamp:14`).

**No `ia_get_snapshot` HTML passthrough.** Raw Wayback HTML is rewritten by the archive (banner injections, relative URL rewriting) and can be very large. The tool strips an HTML page to readable text in lines (links come back as data under `include_links`, not as markup) and always returns the replay URL so the human can open the original in a browser. Another text type (plain text, JSON, XML, JavaScript) has no markup to strip and is returned as stored.

**Non-HTML text is read from the `id_` form.** The replay form rewrites URLs inside JavaScript, CSS, and XML, which would hand callers text the site never served. The `Content-Type` of the replay response decides: HTML or no type is read from the replay, any other `text/*`, JSON, XML, or JavaScript type has that body cancelled unread and is read as stored from the capture's `id_` URL in a second request under the same timeout and retries, and any other type fails as `non_text_capture` naming the replay URL, since a PDF or image has no text to return and a mangled decode would read as success.

**`ia_get_snapshot` pages its text like `ia_get_text`.** A capture longer than one page must stay readable past its first 50,000 characters. `max_chars` (default and ceiling `IA_MAX_SNAPSHOT_CHARS`) and `char_offset` count UTF-16 code units, and `has_more` and `total_chars` describe the text read from the first 4 MiB. A snapshot has no cursor: the next-page notice names the `url` and the `resolved_timestamp` to pass as `timestamp` so every page comes from one capture instead of re-resolving a nearest-capture lookup that could land elsewhere; after an archived redirect that `url` is not the one sent (below).

**`include_links` returns links as data, on the page where each starts.** Writing `label (URL)` into the text would grow pages by 93–285%, and returning every link on every call runs to 6.4 MB on a large capture (the PyPI front page), so links are opt-in and separate from `text`. Each http(s) target is listed once, at its first anchor, with the first non-empty text it is linked by, on the page where that anchor's text starts: a read that follows `has_more` meets each link once, and a smaller `max_chars` carries fewer per call. The last page also takes a link starting at the very end of the text (an image-only link after the last text), and the one page of an empty text lists its image-only links, or a read that follows `has_more` would never see them. A label can come from a later anchor than the one its position is taken from, so it can fall on a later page than its link (4 of 2,389 on one capture). An href Wayback rewrote (a raw `/web/…` path, or an absolute or protocol-relative URL on a Wayback host that the capture-URL reader reads) is read once back to the URL it archives; any other href resolves against the first `<base href>`, read the same way, else the page's original URL (an unparseable base falls back to it). Resolving against `replay_url` was rejected: Wayback rewrites `mailto:` and `ftp:` into http-looking capture URLs, and it breaks on originals with no path. Only http(s) is kept, checked after un-rewriting; the fragment is dropped and the page itself is left out. The links come from the same bytes as the text, so within the same first 4 MiB, and cost no request.

**Timestamps take 1–14 digits or ISO 8601 and are normalized before any request.** `timestamp`, `from`, and `to` accept `YYYYMMDDHHMMSS` or a prefix of it, or an ISO 8601 date or UTC date-time; an invalid or impossible one is `invalid_timestamp` instead of a value Wayback would misread. A prefix names a period: `from` starts it, `to` ends it, and a closest `timestamp` resolves to the capture nearest its end (`2015` can resolve to early January 2016). A blank `ia_get_snapshot` `timestamp`, or an omitted or blank one in `ia_find_snapshots` closest mode, reads the timestamp of a Wayback capture URL passed as `url`, else the latest capture. A reversed `from`/`to` range passes through to CDX and answers an empty list with a notice, as a reversed date range does in `ia_search_items`.

**A Wayback capture URL in `url` is read as its original URL plus a timestamp.** `replay_url` is what both Wayback tools return, so a caller passes it straight back; looked up as it stands, it almost always has no captures and reported a capture that exists as missing. A few capture-URL keys do hold captures of their own — Wayback's redirects, recorded when a crawler followed a capture URL — and the reader gives up that literal reading: such a URL answers with its original's captures, and paired with one of its own capture timestamps it fails as `ambiguous_timestamp`. One reader (`src/services/wayback/wayback-capture-url.ts`) serves both tools before any request: `web.archive.org` or `wayback.archive.org`, `/web/<digits>[<xx>_]/<original>`, any two-letter replay modifier dropped. `<original>` is the raw rest of the value, never a parsed `URL`, which would resolve dot segments and split off a query the original keeps; a percent-encoded scheme is decoded once. The same module reads a page's link targets for `include_links` (`hrefTarget`). Calendar, timegate, and timemap URLs name no single capture and pass through unchanged. An explicit `timestamp` that differs from the URL's (compared as normalized digits, so a prefix differs) fails as `ambiguous_timestamp` rather than silently winning, so the content served is never dated by a value the caller did not mean; an embedded timestamp the `timestamp` field would reject fails as `invalid_timestamp` with `field: "url"`. Messages, logs, and the next-page notice name the original URL — the notice names the capture served instead when that original is itself a capture URL, which would read at its own timestamp — so following the notice never fails as `ambiguous_timestamp`, and a history cursor stores it, so `resume_key` continues with either spelling of `url`.

**Text extraction is one linear markup scan, then one reference decode.** It serves archived pages (`htmlToText`) and item descriptions (`descriptionToText`, which keeps paragraph, `<br>`, and list-item breaks as lines and writes a link as its label followed by its URL), so it lives in `src/services/html-text.ts` beside `html-entities.ts` rather than under `wayback/`, shared by the Wayback and Metadata services. A hand-written left-to-right index scan (comment, script/style with raw-text body, any other tag; a quote opens an attribute value only after `=`, as in a browser) hands each construct to its consumer. A description reads a text-level element's tag (`b`, `i`, `span`, …) as nothing and any other construct as a space. A page feeds a line builder that holds each separator until text follows, never revisiting what it wrote beyond its last character: a block element or `<br>` starts a line, the cells of a table row are separated by tabs (empty cells included), `<pre>` text is kept as written apart from whitespace at a line's end, and other whitespace collapses to one space with blank lines collapsed to one. The start and end tags of text-level elements (`a`, `b`, `span`, `sup`, `wbr`, …) add no separator, so punctuation stays on its link and a word that changes style partway stays whole; blocks and cells have their own separators, so a tag need not stand in for one, and every other tag (`img`, `input`, `svg`, `rt`, a comment, a name the scan does not read) still reads as a space. One space stays between a link and the element beside it, with a letter or digit outside CJK (Han, kana, Hangul, CJK punctuation, fullwidth forms) on each side: among the tags between the two words, an end tag comes directly before a start tag other than `<sup>` or `<sub>`, and an `</a>` that closes an open `<a>` or an `<a>` start tag comes. A link and the element on either side of it (an edition menu, a country list, a name and its flair badge, a timestamp and the category link after it) are separate items a stylesheet spaces apart, while a `<sup>`/`<sub>` note marker and CJK runs join as written. Elements that meet with no link among them stay joined: markup alone cannot tell a price beside its screen-reader label from IPA letters in sibling spans, combining marks, or a heading set one letter per span. An `</a>` with no `<a>` open, which the HTML parser drops, counts as no tag. A block or `<br>` between a cell's tab and its text drops the tab (as in the `<td><ul>` cells of `iana.org/domains/reserved`); carrying it onto the new line would lengthen those pages' text. On a page, a `<template>`'s content reads as nothing up to its matching end tag (unclosed, to the end of the page, as an unclosed `<script>` does), unless the template declares a shadow root (`shadowrootmode` `open` or `closed`), which browsers render. The content of a phrasing element (the text-level elements plus replaced and form elements such as `button`, `select`, `svg`, and `iframe`) also reads as nothing when its own start tag hides it: a `hidden` attribute other than `until-found`, unless an inline `style` declares another `display`, or an inline `style` whose winning `display` is `none`, read as CSS tokenizes a declaration list. The hidden part ends at the element's own end tag, at an end tag of an element it did not open, or at the next `<br>`, block, or cell tag (a hidden `<a>`, or a hidden part opened inside an `<a>`, also at the next `<a>` start tag), so an unclosed one removes at most the rest of its line. Only phrasing elements are hidden because pages hide blocks in order to reveal them on a click or by script (carousels, side panels, collapsed lists); classes, stylesheets, `visibility`, and `aria-hidden` are not read. Neither a template nor a hidden part opens inside an element whose content a browser reads as text (`textarea`, `title`, `xmp`, `iframe`, `noembed`, `noframes`). A description leaves out neither: it keeps template and hidden content. The same scan records each `<a href>` outside a template or hidden part and the first `<base href>` outside a template for `include_links` (below). References are decoded in one callback pass over each text run, against a curated `Map` (HTML 4.01's 252 names plus `apos` and the WHATWG upper-case aliases) with WHATWG numeric rules; decoding per run keeps a reference split by markup inside `<pre>` from being reassembled. Decoding once rules out double-unescaping; no dependency is needed, since a 20-page 1996–2015 corpus used no name outside that table. The scan is index arithmetic rather than a regex so it stays linear on adversarial archived pages in any engine — the earlier regex chain went quadratic, and a regex alternative measured linear in V8 still hit JavaScriptCore's backtracking-stack fallback on long tags under Bun.

**Decode by declared charset.** A replay's `Content-Type` often names no charset, so the body is decoded from bytes: BOM, then header charset, then, for HTML only, the first `<meta>` declaration in the first 16 KiB (past the ~1 KiB banner Wayback injects); in plain text, JSON, XML, or JavaScript, `<meta>` markup is content and is not read. A body that declares none stays UTF-8 when a strict UTF-8 decode succeeds; only bytes that are not UTF-8 fall back to Wayback's `x-archive-guessed-charset` (when `TextDecoder` knows the label), else windows-1252. The guess never overrides valid UTF-8 because it is unreliable — a Latin-1 slashdot.org 1999 capture is guessed `ibm852`, and a wrong single-byte guess would turn a valid UTF-8 page into mojibake. On a body cut at the read limit, a character split at the cut is dropped before the strict check, so the cut cannot fail it.

**Read at most 4 MiB of a replay.** The body is streamed and cut at 4 MiB, cancelling the upstream read, and the tool discloses the cut in a `notice`. Measured on 2024 captures of heavy pages, a 3.0 MB edition.cnn.com front page yields all its text within 1.3 MB and Wikipedia articles reach 50,000 characters within 440 KB, so ordinary pages lose nothing.

**Report the capture Wayback served.** A replay answers with two kinds of redirect. Wayback's own 302 sends a timestamp that is not itself a capture to the nearest one, with no `Memento-Datetime`. An archived redirect is a capture of the site's own 3xx, replayed with that status, its `Memento-Datetime`, and a `Location` naming the target's capture URL. Both are followed. `replay_url` is the URL the redirects ended on (always `https://web.archive.org`: a hop to the `wayback.archive.org` alias is requested where its `Location` points and reported in its `web.archive.org` form, so the timestamp and the `id_` read come from the capture served), `resolved_timestamp` is read from it, and `resolved_status` is the HTTP status of that final replay response (Wayback's own `x-ts` header carries the same value), so all three name the capture the text came from — never the capture the lookup resolved. After an archived redirect the text is another URL's page, so the `notice` names each archived redirect's status, capture timestamp, and target, and the next-page notice names the URL the served capture archives, which reads the next page from that capture directly.

**The service follows replay redirects, not the runtime.** Replay requests are sent with `redirect: 'manual'`, and each `Location` is resolved against the URL that answered it. Wayback writes many archived redirects' `Location` root-relative with the target embedded (`/web/<timestamp>/http://…`), a form Bun's `fetch` refuses to follow, so leaving redirects to the runtime made one call succeed on Node and fail on Bun as an outage. Following them in the service also tells the two kinds apart and lets an error name how the redirects ended. The walk is bounded: at most 10 redirects, only to http(s) URLs on the Wayback Machine hosts, ending at a URL already requested, each request under the call's deadline with the time that remains. Redirects that reach no readable capture are `no_snapshot_available` after one attempt: the target of an archived redirect was never archived (a 404 without `Memento-Datetime`), is an archived error page, or was refused, or the redirects loop, run past 10, or carry no `Location` or one that cannot be followed. The message names the archived redirect and its target, where reporting no capture of the requested URL would be false: that URL was captured, as a redirect. A 5xx, 408, 425, 429, timeout, or network error on any request keeps the handling it has on a single request, and a retried attempt starts the redirects again from the first URL.

**Closest lookup falls back to CDX.** The Availability API sometimes answers `{}` for URLs CDX has captures of, and it fails more often than CDX does (a 429, a 5xx after its retries, an HTML error page, or an HTTP 200 whose body carries an `error` in place of a capture, as when its own lookup times out), so an empty answer or one of those failures triggers one CDX `sort=closest` query on its different host. An `error` body is not retried: a lookup the Availability API could not finish in its own time is what the fallback's longer ceiling is for. A usable capture in the same body is still returned. A timeout, a network error, a 4xx refusal, and a cancellation never fall back. A successful Availability answer costs one request. The fallback gets one attempt, under the least of 25 s, the request timeout, and the time left in the call's deadline (below): measured `sort=closest` latencies ran 2.5–23 s for about half the URLs tried and 31 s to over 60 s for the rest, so no retry ladder could help. A fallback that fails or times out is `cdx_unavailable` after an empty answer, `availability_unavailable` after a failure (`content_fetch_failed` in `ia_get_snapshot`), with a history-mode hint — never `no_snapshot_available`, which would claim there is no capture.

**Upstream non-2xx answers surface as a declared reason, never with the upstream body.** `fetchWithTimeout` throws on every non-2xx with the body in `data`, so each service reclassifies inside its retry closure, allowlisting what `data` carries: CDX → `cdx_unavailable`, Availability → `availability_unavailable`, Advanced Search → `search_unavailable`, Metadata API and text downloads → `archive_unavailable`. A 5xx, 408, or 425 keeps `retryAfter`/`retryable`, so attempt counts are unchanged (Advanced Search treats 408 and 425 as refusals). A 429 is answered after one request with a hint to wait (the `Retry-After` value when it is delta-seconds or a future HTTP-date, otherwise several minutes) — retrying it would only extend a rate limit that, measured, held for 5–13 minutes. The retry predicate stops it rather than `retryable: false`, which would put "not retryable" on the wire beside a hint to wait and retry. Any other 4xx is a refusal no retry fixes: answered after one request with `retryable: false` and a throw-site hint naming what the caller can check (the query, the identifier, the item's file list, `url`/`from`/`to`/`resume_key`, or `url`/`timestamp`), since each declared recovery promises a later retry. A 401/403 text download stays `download_forbidden`, and a 403, 410, or 451 from a Wayback API is the URL not being served (below). An HTML page or unparseable JSON on a 200 is treated as the same reason and retried like a 5xx. `ia_get_snapshot` maps any `ServiceUnavailable` from lookup or fetch onto its own `content_fetch_failed`, keeping its hint and retry fields, since the service cannot know which tool's reason set applies.

**Timeouts and network errors surface as the same declared reason.** A request timeout — `fetchWithTimeout`'s own deadline, on the headers or a stalled body — is not retried on the Wayback and Advanced Search paths: the attempt already waited the full `IA_REQUEST_TIMEOUT_MS` on an upstream that did not answer, and further attempts would hold the caller past common client tool-call timeouts. The Metadata API and text download paths retry a first timeout once, while the call deadline has time left, and end the call on a second: archive.org's metadata and download hosts stall intermittently and usually answer a second request, which a single attempt turned into `archive_unavailable`. A `ia_get_text` download that timed out or that the call deadline cut off can stall again on a later call, which its declared recovery says. A network error (refused, reset, a DNS failure, or a connection dropped mid-response) fails fast, so it keeps its four attempts. Both surface after the retry loop as that path's reason (CDX → `cdx_unavailable`, Availability → `availability_unavailable`, page fetch → `content_fetch_failed` through the tool, Advanced Search → `search_unavailable`, Metadata API and text download → `archive_unavailable`), without `retryable: false`, since a later call can succeed. The classification, the retry predicate, and the 429 wait phrase live in one module (`src/services/upstream-errors.ts`) that all three services share. So does a redirect chain `fetchWithTimeout` refuses to follow — past 127 hops, or to a URL that is not HTTP or HTTPS — after one request, its message naming what the upstream did, in place of the framework's hint to request the final URL directly, which only fits a URL the caller chose. Caller cancellation and a caller-side deadline pass through untouched.

**One deadline spans each call.** Each tool and resource handler starts one clock before any request: 55 s, or `IA_REQUEST_TIMEOUT_MS` when that is longer (`src/services/call-deadline.ts`), and passes it to every service method it calls. Every request the call chains gets the lesser of the request timeout and the time remaining; no request is sent with 1 ms or less left; and every retry ladder runs under `withRetry`'s `deadlineMs` set to what remains, with the caller's signal kept separate, so a ladder stops when the call runs out rather than after its fourth attempt. At the default the call settles before the 60 s default request timeout of MCP SDK clients, with 5 s left for the request's trip in, response handling, and the trip back; a longer request timeout raises the deadline to it, since only a client that waits longer could use it. A call that runs out — mid-request, mid-backoff, or before a request — fails with the path's declared unavailable reason, its message naming the deadline, without `retryable: false`; an answer that completed as it ran out and would have ended the ladder anyway (a 429, a refusal) is reported as itself, and a caller cancellation stays `RequestCancelled`. Inside the deadline nothing changes: attempt counts, which failures retry, and the Metadata/download retry of a first timeout, which a request the deadline cut short never triggers. This replaces the closest-capture lookup's own deadline (the request timeout plus 25 s) and history mode's 45 s deadline, whose expiry surfaced as a bare `Timeout` with no reason; it is now `cdx_unavailable`. Without a call-wide bound, chained ladders (a closest-capture lookup, the replay, and the `id_` read of a text capture) could run past 5 minutes at the default timeout, long after a default client had abandoned the call. Calls that used to succeed only after 55 s now fail, retryably; a default client had abandoned most of them already.

**`archive_unavailable` is one reason for both item tools and the resource.** `ia_get_item`, `ia_get_text`, and `ia://item/{identifier}` share one Metadata API read — its retry ladder, call deadline, status mapping, and body parse — `ia_get_item` and the resource for the whole record, `ia_get_text` for the file list alone, so a Metadata API failure reaches all three under the same name, message, and hint; `ia_get_text`'s download failures use it too, since no existing reason's recovery was true for them (`download_forbidden` says the item is restricted). Its `ia_get_text` recovery adds that a download that timed out or that the call deadline cut off can stall again on retry.

**An archived error page is `no_snapshot_available`, not a Wayback failure.** Wayback replays a capture of a site's 4xx or 5xx page with that status and a `Memento-Datetime` header (RFC 7089), which a Wayback failure of its own does not carry. The replay fetch captures that header on a non-2xx, and a 4xx or 5xx carrying it is not retried and surfaces as `no_snapshot_available`, naming the capture timestamp and archived status, on the exact-timestamp and lookup paths alike; a 3xx carrying it is an archived redirect, which is followed. `content_fetch_failed`'s retry hint would be false for it, while history mode with `status_filter: "200"` finds a readable capture. Returning the error page's text as a success was rejected: it turns a failure into a success shape. Without the header, a 429 is still answered after one request, a 5xx, 408, or 425 retried, and a 404 is `no_snapshot_available`. The `id_` read of a non-HTML text capture is the exception: the replay already served that capture, so an `id_` 4xx, an archived error page, or redirects that reach no capture say nothing about it and surface as `content_fetch_failed`, never as no capture.

**A replay 4xx without `Memento-Datetime` is Wayback refusing the request.** Wayback answers a site excluded from the archive with a 403 and its own playback page, no `Memento-Datetime`. Every such 4xx except the 404, 408, 425, and 429 above is not retried and surfaces as `no_snapshot_available` naming the status, never carrying the playback page as `data.body`. A 403, 410, or 451 says the Wayback Machine does not serve the URL and overrides the declared history-mode hint, which cannot help: no capture of an excluded URL can be read at any timestamp. Another 4xx (a 400 for a malformed replay URL) keeps the declared hint. After an archived redirect a refusal concerns the redirect's target: the message names that target, never the requested URL, and the declared hint stays.

**A lookup 403, 410, or 451 is the URL not being served, not an outage.** CDX answers the same excluded site with a 403. History mode, the closest-mode CDX fallback, and the Availability API all map 403, 410, and 451 to `no_snapshot_available` after one request, with the replay's message and hint (shared from `wayback-service.ts`). `cdx_unavailable` was rejected for it: its "did not complete, retry" framing sends callers back to a URL that can never be read, including through `ia_get_snapshot`, whose timestamps shorter than 14 digits resolve through the fallback. The fallback lets this answer through unwrapped; a lookup failure it wraps drops "retry later" only when every answer the lookup got was a refusal.

**`ia_get_text` separate from `ia_get_item`.** `ia_get_item` returns metadata + file manifest, not content. Fetching text content is a distinct, potentially large second request. Keeping it separate lets agents skip it when they only need metadata and file URLs.

**Text continuation keeps a decoder checkpoint.** Text pages count UTF-16 code units and match slicing the whole decoded file, including BOMs, malformed UTF-8, and a page boundary inside a surrogate pair. An opaque, expiring tenant-scoped cursor binds the item, selected filename, and stable representation validator to a byte checkpoint and intra-character skip. Conditional identity-encoded Range requests resume there; the response status, range, and validator must agree before decoding. No document text is stored. Offset paging remains available when a validator or cursor storage is unavailable, with a notice. Memory stays bounded by the page and lookahead; `max_chars` retains its configured cap and `source_file_bytes` reports manifest bytes rather than a guessed character count.

**Collapsed history uses an unreturned timestamp.** For exact URLs under every `collapse` value, one extra row identifies where the next page begins. The tenant-scoped expiring cursor retains the query filters and resumes inclusively at that row's timestamp, preserving page boundaries while allowing a different page size. Every collapse value pages this way because CDX's own key skipped a capture at a page boundary under `timestamp:20`, and under `timestamp:0` at `limit` 1 returned a key whose next page was empty. A `url` with a `*` in the middle is read as part of the URL, as CDX reads it, and takes the cursor too. Legacy CDX keys and wildcard histories (a trailing `*` or a leading `*.`) keep their existing path with an incompleteness notice: a wildcard page can omit the row at a page boundary or return it as a later capture of the same URL, and a `limit` that holds the whole listing (up to 10,000 rows) avoids both. A byte offset or CDX raw resume key cannot supply the same collapsed-page guarantee.

**A `digest` cursor stores the lookahead digest and a row count.** Collapsing on `digest` lists a capture only when its digest differs from the capture before it, so a page boundary needs more than a timestamp: the cursor keeps the next row's digest and `returned`, how many rows of the listing at that second earlier pages returned. A resumed page asks for `limit + 1 + returned + 1` rows, drops `returned` rows, then drops one more only when the next two rows confirm a capture the unpaged listing had collapsed (the first does not carry the digest, the second does). Dropping rows until the first one carrying the stored digest was rejected: when one second's digests run A, B, A it never ends at `limit` 1. The lookahead's digest always differs from the row before it in the listing, which makes the count rule exact; the joined pages equal the unpaged listing at every `limit`. The extra fields are optional, so cursors issued before them still parse.

**Partial dates expand at the search boundary.** `date_from` uses the first day of a requested year or month, and `date_to` uses its last day under Gregorian leap-year rules. Invalid dates fail before HTTP with `invalid_date_range`; the advertised inputs remain free strings so the error can name the field and recovery. Blank bounds are omitted, and reversed valid ranges retain the upstream empty-result behavior. The bounds filter the publication `date` field only, so an item with no `date` never matches a range; an upload-time range is `publicdate:[2026-11-01 TO 2026-11-21]` in `query`, where a bare upper date covers its whole day, and the descriptions of both bounds say so.

**`ia_get_item` pages the manifest in the handler, not the service.** Most items have a few dozen files, but scanned books and collections carry hundreds to thousands (mostly per-page derivatives), which put megabytes on both response surfaces. The handler filters by `format` and slices by `max_files`/`file_offset` so `structuredContent` and `content[]` carry the same page; `ArchiveMetadataService.getItem` returns the full manifest and the handler pages it; `ia_get_text` reads the item's file list on its own. Truncation and the match count go through the enrichment block (`truncated`, `totalCount`, `notice`) rather than a domain field.

**Over-cap `max_files` and `limit` are served at the cap.** Both are workload caps on a read, so a value between the cap and a hard ceiling is served at the cap rather than rejected: `max_files` 501–300,000 at 500, history-mode `limit` 10,001–150,000 at 10,000 returned records. Exact-URL histories under any collapse request one additional row for continuation (a resumed `digest` page asks for its `returned` rows more). When the cap withholds results the response sets `truncated`/`shown`/`cap` with the applied value and a notice naming the next `file_offset` or `resume_key`. Closest mode never reads `limit`.

**Metadata API `{}` empty response = not found.** The API returns HTTP 200 with `{}` for unknown identifiers rather than 404, so the service throws `item_not_found` for it. The same goes for any body with neither `metadata` nor `files`, which is no item, though it would otherwise read as one with no metadata and no files. An identifier with a `/` in it addresses a sub-path, which answers `{"error": "Couldn't get 'b' for item a"}` or a bare `{"result": …}` with HTTP 200, so the tools reject a value holding `/` or `:` that is not an archive.org item URL as `invalid_identifier` before any request; `ia://item/{identifier}` needs no check, since the SDK's URI template refuses a `/`. On the file list every one of these answers, a dark item's `error` included, is `item_not_found`. An identifier that names no item once its dot segments resolve — a bare `.` or `..`, or `../` from an item URL, whose `%2F` archive.org decodes — would land on `/metadata/`, another item's record, or archive.org's home page, which the retry ladder read four times as an outage, so it is `item_not_found` before any request.

**`ia_get_text` reads the file list, not the whole record.** It uses only `files`, and a record can dwarf its list (`micro_IA40244325_0031`: a 21 MB record, 1.4 MB on the wire, against a 6.5 KB list), fetched again for every page. `GET /metadata/{identifier}/files` returns the same entries. Any body but a `result` list is `item_not_found` with one message naming an unknown or a dark item: telling them apart takes a second request (`/is_dark`) that can itself fail. Carrying the chosen file in the cursor was rejected: the first page still pays the full read, and the cursor would pin a manifest that can change.

**Item URLs are read as the identifier they name.** `identifier` accepts an `archive.org` or `www.archive.org` URL whose path is `/details/`, `/download/`, `/metadata/`, `/stream/`, or `/embed/` followed by the identifier, or a storage-node URL (`<node>.archive.org/<n>/items/<identifier>/…`), because that is what a caller copies from the browser or a search result; `ia_search_items` `collection` accepts the `/details/` form and matches any other value as given. A download, stream, or storage-node URL's file acts as `ia_get_text`'s `file`, and a continuation must read that same file. A Wayback capture URL is `invalid_identifier` with a recovery pointing at `ia_get_snapshot`; a bare identifier holds only letters, digits, `.`, `_`, `-`, and a leading `@`, so anything with `/` or `:` is parsed as a URL, with the query and fragment dropped and the message never echoing the value.

**`ia_get_text` reads one readable text file, chosen by rule.** An item can hold several (one per volume), so `file` names the one to read, as `ia_get_item` lists it. The default is the first DjVuTXT file, else Text, else Plain Text, else another `.txt` file, with `Metadata`-format sidecars excluded because they are not the item's content. When several are readable, a notice gives the count and says how to list and pass them, so a multi-volume item is never read as one document unannounced. A `file` outside the manifest or not readable text is `invalid_file`.

**`find` is a streaming phrase match, never a regular expression.** `compilePhrase` trims the phrase and turns each White_Space run into one token, and a Knuth–Morris–Pratt matcher over those tokens reads the download as it streams, so the cost stays linear in the file and memory stays bounded by the page. Letters match under simple case folding, one character to one (`ß` never matches `ss`). `toLowerCase` and `toUpperCase` cannot supply it (they merge `ı` into `i` and split `ﬅ` and `ﬆ`), so the fold classes are read once from the runtime's own case-insensitive Unicode regex engine; Bun and Node carry different Unicode data and can differ on a rarely used character. A whitespace run in the phrase matches any White_Space run in the text, line breaks included (`Mr.  Darcy` finds `Mr. Darcy`); `P  ember  ley` and `Pem- \nberley` do not find `Pemberley`. White_Space decides what is blank, not `String#trim` (which keeps U+0085 and strips U+FEFF), so the tool asks `compilePhrase` whether a `find` holds a phrase and sends none otherwise. The page starts at the first match at or after the start offset and is the page a read there would return; `next_continuation` searches on from its end, so a match that begins inside the page and runs past its end is not reported by that search.

**`find_incomplete` has two causes, both resumable.** The search stops a margin before the download's request timeout or the call deadline (1 s, or a tenth of a shorter timeout; 29 s at the default 30 s), so a download that stalls mid-search surfaces as a resumable stop instead of a timeout that loses the position: no match begins from the start offset up to the resume point, which is the start of the earliest partial match still in progress, so only that match's bytes are read again. It is returned from inside the retry closure and thrown after it, never retried, since a retry would restart the search and stall again; a caller cancellation is rethrown and is never a miss or `find_incomplete`. The error names only a call that reads past where this one began: the continuation, whose ranged read starts at the resume point's byte, or, with no cursor stored, `char_offset`, which reads the file from its first byte again and so gets further only on a faster download. A search that did not get past its start, with no cursor beyond the bytes it read (an offset read that stopped before its decoder reached `char_offset`, or a read that stopped where it began), has no such call, so it fails as `archive_unavailable`, as a read without `find` does when its download cannot reach `char_offset`. It is thrown after the retry closure too, one download instead of that read's timeout retry: at the default timeout the retry would get only what is left of the call deadline to cover the same bytes. The second cause is the held-text bound. The matcher holds text from the earliest partial match, capped at `max_chars + 1 + 2 × phrase length` UTF-16 units. When the first match completes after the call has released the text at its start, which takes whitespace between two overlapping partial matches longer than about twice the phrase and the page bound, the call throws `find_incomplete` whose `char_offset` is the match itself, and calling again there hits. An in-call ranged re-read was not built: it would add its own validation, deadline, and failure paths for a text shape that needs a whitespace run longer than a page.

**Advanced Search empty query = HTML fallback.** The API returns an HTML error page (not JSON) when `q` is empty, so a blank query must never reach it. The `query` schema enforces that (see the next note), so the service carries no guard of its own.

**Required strings reject blanks at the schema.** `query`, both `identifier`s, and both `url`s are `z.string().trim().min(1)`. A blank value is structurally wrong and no tool-specific guidance would help, so it belongs on the schema, where it also advertises `minLength: 1`; each `.min(1)` message names what to send. Surrounding whitespace is trimmed before the handler runs.

**`mediatype` resolves in the handler, not through `z.enum`.** Solr matches `mediatype` exactly and case-sensitively, so `text` or `Texts` answered zero results as an empty success. The handler trims, lowercases, maps a fixed alias table (`text`/`book`/`books` → `texts`, `movie`/`video`/`videos` → `movies`, `images` → `image`, `collections` → `collection`), and rejects anything else as `invalid_mediatype` listing the ten values. A `z.enum` would reject the near-misses instead of resolving them, and `z.preprocess` does not serialize to JSON Schema. The ten values are the full vocabulary of the index (an aggregation over it, 2026-09-24); a blank `mediatype` still means no filter.

**Closest mode reads an omitted `timestamp` as the latest capture.** The closest-capture lookup already resolves no timestamp to the newest capture, and `ia_get_snapshot` sends it for a blank one, so `ia_find_snapshots` closest mode does the same, one lookup for both tools. The earlier rejection (`missing_timestamp`) replaced a misleading `no_snapshot_available` before that reading shipped on `ia_get_snapshot`; once it did, a rejection that names the field only cost a caller the extra call, since the intended answer is unambiguous. A URL with no captures fails as `no_snapshot_available`. A capture URL's own timestamp applies first. `mode` stays required: `{ "url": … }` alone could mean history or closest. `ia_get_snapshot` keeps `timestamp` a required key, sent blank for the latest capture: making it optional changes the advertised `required` list and the validation outcome for existing clients, so it waits for a breaking window.

**An empty search page says why.** Advanced Search answers a page past the end with `numFound > 0` and no docs, so the empty-result notice distinguishes that case (naming the last page) from a search that matched nothing (naming every filter applied, if any).

**An empty history page says why, and never quotes the URL.** CDX answers a history query nothing matches with an empty list, and an empty list means CDX listed no rows, so history mode returns `snapshots: []` and one notice instead of failing: the Wayback Machine lists no captures of the URL (or none under its prefix or domain), none match the `from`, `to`, and `status_filter` sent (the remedy names only the fields sent), or none remain past the `resume_key`; a page that is empty but carries a CDX key says to pass it on. The notice quotes only field names and values as sent to CDX (digits and a status code), never the URL, because a notice renders as live Markdown. The service's continuation-limitation notice is appended, not copied. A refusal (403, 410, 451) stays `no_snapshot_available`, and an outage, an HTML page, unparseable or non-list JSON, a timeout, and the call deadline stay `cdx_unavailable`, so an empty list is never an unread answer. `queryCdx` requires the body to be a list of rows of strings, because a `200` of any other JSON would read as no rows.

**Advanced Search error bodies are errors, never empty pages.** A rejected request comes back as HTTP 200 with `{"error": "…"}` and no `response`, so the service checks for `error` before reading `response`; a genuinely empty result still carries `response` with `numFound: 0`. An untagged message (a query parse error), `[UNSUPPORTED_SORT]`, `[MALFORMED_QUERY]` (an unquoted URL), and `[UNSUPPORTED_VALUE]` (a `q` past 2,047 characters, filters included) blame the request and surface as `invalid_query` with the upstream text, its whitespace collapsed to one line; `[BACKEND_ERROR]` and any other tag surface as `search_unavailable`. `[BACKEND_ERROR]` was only ever observed for query text — a bare `AND`, `title:`, `AND AND`, or `&`, `%`, `/`, `!`, `;` inside a word (`AT&T`, `100%`, `1/2`), deterministic on repeat and cleared by quoting the phrase behind a field prefix — but it names a backend fault, so it stays `search_unavailable` with a recovery naming those inputs. Neither is retried (`retryable: false` on the unavailable case), so the recovery promises no retry for them. A 5xx is retried, and a 429 or another 4xx answered after one request, the 429 with a wait hint and the 4xx with `retryable: false` and a hint that repeating it will not help (a control character in `q` draws a 400), neither carrying the upstream body; an HTML page, unparseable JSON, a body with neither key, or a `response` whose `docs` are not a list of records is retried like a 5xx, while an absent or `null` `docs` reads as no rows. Those outages, a timeout and a network error included, carry their own hint that Advanced Search is down, since the declared recovery's query-text advice is wrong for a query that never reached the backend.

**`query` is capped at 2,047 characters.** Advanced Search rejects a composed `q` longer than 2,047 characters as `[UNSUPPORTED_VALUE]`, so a longer `query` can never succeed; the schema rejects it before a request, and a shorter one that the filters take past the limit still reaches `invalid_query`.

**Ties under the sort break by `identifier`.** Advanced Search orders tied rows arbitrarily from one request to the next, so consecutive pages repeat and skip them: 28 and 43 of 200 rows overlapped between pages 1 and 2 of `downloads:0 AND subject:news` sorted `downloads desc`, in two runs on 2026-10-12. Every search therefore sends `identifier asc` as a second `sort[]`, which made that overlap 0 and left the first page of a query without ties (`tesla`) in the same order. A `random` sort is sent alone, since Advanced Search rejects any other sort beside it. There is no relevance sort: `score desc` and `relevance desc` are `[UNSUPPORTED_SORT]`.

**The 10,000-result window is checked before any request.** Advanced Search rejects a page whenever `page × rows` exceeds 10,000 (measured at rows 1, 7, 30, 50, and 200, for queries matching 0, 286, and about 75,700 items), so the handler throws `page_limit_exceeded`, naming `floor(10000 / rows)` as the last reachable page. It checks the `rows` actually sent, after the 200 cap. Reaching results past the window needs the cursor-based Scraping API, which would replace `page`.

**Over-cap `rows` is served at the cap on page 1 only.** A `rows` from 201 to 10,000 has one reading on page 1 — as many as one call allows — so it is served as 200 with `truncated`/`shown`/`cap` and a notice naming `rows: 200, page: 2`, which resumes at result 201. On later pages it rejects as `rows_over_cap`: pages are `rows`-sized blocks and Advanced Search ignores a `start` offset, so the remainder of a 500-row page 2 starts at result 701, which no `rows`/`page` pair at 200 addresses. The output `rows` reports the applied value, so the past-last-page arithmetic stays consistent. Above 10,000 no request can be served, so the schema rejects it.

**Search results drop `fav-` collections and cap `creator` at 10.** Advanced Search lists a `fav-<account>` entry among an item's collections for every account that favorited it — hidden per-account lists, absent from the item's own metadata — which put a default 50-row `tesla` page at 231 KB (2026-10-12; 11 KB without them). They are filtered by prefix, never by position, since real collections can follow one; `collection` is omitted when nothing else remains. `creator` keeps its first 10 names (an 8,613-item sample peaked at 8; large collaborations run to 409) and a per-row `creator_count` gives the full count when it was cut; `ia_get_item` returns the full list. `title` and `date` arrive as lists on a few records and are relayed as received by `ia_search_items` and `ia_get_item` alike in `structuredContent`, as is `publicdate`; `ia_get_item` relays every metadata field the same way (below).

**List-valued fields keep their value boundaries in `content[]`.** Joining a list with `, ` (and an `ia_get_item` `description` list with line breaks) made a value holding a comma or a line break indistinguishable from two values, which `structuredContent` keeps apart. `ia_get_item` and `ia_search_items` share one renderer (`src/mcp-server/tools/labelled-field.ts`): a string or a one-value list renders inline after its label, as before; a list of two or more renders the label line, a blank line, one `- ` item per value through `escapeMarkdownInline` (a line break kept as a hard break), then a blank line. The blank line after the label keeps an empty first item from reading as a setext underline of the label; the one after the list keeps the next line from continuing the last item. A multi-value `title` is listed under `**Title:**` and the heading falls back to the identifier, as for an absent title, since no one value is the title. The renderer appends line by line, since spreading a long list into `push` overflowed the call stack past about 120,000 values. It takes an optional per-value renderer (default `escapeMarkdownInline`): `ia_get_item` renders each `licenseurl` value as a link when it is an absolute http(s) URL and as the escaped value once otherwise, so a license such as `CC0 1.0` is not shown twice as `CC0 1.0 (CC0 1.0)`.

**Every relayed item metadata field goes through one string-or-list parse.** Casting each field to a string kept failing output validation or crashing on a list value (`title`, `date`, `rights`, `licenseurl`, `volume`), so `ia_get_item` and the resource read every relayed field with one parse: a string or a list of strings is relayed as received, and a value of any other shape is left out, a list holding any non-string included, since a filtered partial list would read as complete. `rights`, `licenseurl`, and `volume` have arrived as lists; `mediatype`, `runtime`, and the Open Library IDs are widened by the same rule with no list observed. An output-validation failure on a metadata field is then impossible by construction, and `description` is parsed before it is converted to plain text, which also removes a crash on a numeric or list `description`. A list `mediatype` whose every value is `texts` also gets `image_count`. `ia_search_items` reads each row's `title`, `creator`, `mediatype`, `date`, `publicdate`, and `collection` through the same parse, so a value of another shape is left out of its row and the page still returns every row; a search row holds one `mediatype`, so a list there is left out.

**Each tool relays the date form its upstream stores.** `ia_get_item` returns `publicdate` as the Metadata API stores it (`YYYY-MM-DD HH:MM:SS`, UTC) and `addeddate` as stored (the same, or a bare date on some records); `ia_search_items` returns `publicdate` as Advanced Search does (`2014-10-24T16:15:43Z`). Normalizing either would invent a value the Archive did not state. `addeddate` stays out of search rows. `publicdate` is the upload time, present on nearly every item including those with no `date` (`achristmascarol19505gut` has `publicdate` and `addeddate` and no `date`).

**Manifest entries are read field by field.** The manifest mapping cast `name`, `format`, `size`, and `md5`, so one malformed value failed `ia_get_item` output validation, crashed `ia_get_text`'s file pick, or (a `null` entry, or a `files` value that is not a list) threw a `TypeError` that the retry loop retried. Each entry passes through one reader: an entry that is not an object or has no usable name is left out (lowering `file_count`; a `files` value that is not a list reads as none), and `format`, `size`, `md5`, `title`, `track`, and `length` are kept only as non-empty strings. `source` stays out: it is on every file of every item, texts included, so it would add a field to every row of every manifest.

**Per-file details render as nested items.** `title`, `track`, and `length` of an audio or video file appear in `content[]` as `**Title:**`, `**Track:**`, and `**Length:**` items nested under the file's line, not in a parenthetical, because a track title holding a comma would lose its boundary. They are relayed as catalogued (`length` is `06:21` or seconds such as `381.1`, and the copies of one recording can disagree, so compare within one format; derived copies such as an Ogg made from an MP3 often lack `title` and `track`). `runtime` is the item-level total (`13:06:44` for `pride_and_prejudice_librivox`). The resource carries `runtime` and no per-file fields.

**`creator` matches as a sloppy phrase, not an AND of words.** `creator:"<name>"~N` with N = 2 × (words − 1), the slop a full reversal of the name needs, so `Charles Dickens` finds `Dickens, Charles, 1812-1870` and `Charles John Huffam Dickens`. An AND of the words was rejected: it also matches items whose different creators each hold one word. The index puts 100 positions between one creator value and the next, so a phrase of k words starts matching across two values at a slop of 102 − k; the creator slop stays below that up to 34 words, and a longer name is sent as the exact phrase. A double quote in a filter value is sent as a space, since Advanced Search answers an escaped one with `[BACKEND_ERROR]`; a backslash is escaped. A `creator` or `language` with no letter or digit is `invalid_filter`, because Advanced Search drops such a clause and matches every item.

**`language` expands to every spelling the Archive records for it.** The index stores one language under many spellings (`eng` 25.6M texts, `English` 12.5M, `en` 92K; `scr` 14,781, `Croatian` 3,719, `hrv` 958), so a filter on one misses most records. A known language is sent as the OR of its ISO 639-2/B and 639-2/T codes, ISO 639-1 code, English names, and discontinued MARC codes, from the Library of Congress ISO 639-2 and MARC language lists (`src/services/archive-search/language-spellings.ts`). The `qaa-qtz` local-use range is excluded; a name loses its trailing parenthetical (`Occitan (post 1500)` → `Occitan`) and an inverted name is also given uninverted. A spelling two languages share (`ga`, the 639-1 code of Irish and the name of Ga; `Tonga`) is dropped from both. A two-letter code that is also an English word (`am`, `an`, `as`, `be`, `he`, `hi`, `is`, `it`, `my`, `no`, `or`, `so`, `to`) is sent only when it is the value given, so `Norwegian` does not pull in every record tagged `no`. An unknown value is sent as given.

**A query ending in an unpaired backslash is rejected before the request.** Advanced Search cannot parse a backslash that escapes nothing: alone it is a syntax error, and inside the filter wrap `(<query>) AND …` it escapes the closing parenthesis and surfaces as `search_unavailable`. The service throws `invalid_query` for an odd trailing run of backslashes, filtered or not, so the failure names the query rather than a backend fault.

**CDX array-of-arrays format.** First element is the header row `["timestamp","statuscode",...]`; subsequent elements are data rows. Service strips the header and maps remaining rows to objects by index position. This is stable across CDX field selections.

**`ia_search_items` output includes pagination context.** The Solr API returns `response.numFound` and `response.start`. The output schema must expose `total_found: number` and `page: number` / `rows: number` so agents know whether they're seeing 5 of 5 or 5 of 50,000 results, and can paginate correctly without guessing.

**No DataCanvas.** Capture lists and search results are discovery surfaces — agents use them to find a specific item then drill in, not to run aggregates. `collapse` + `limit` handle large CDX histories at the API level.

**Resource scope is minimal.** One resource (`ia://item/{identifier}`) covers the stable-URI injectable-context use case. CDX history and search results change too fast to be meaningful as resources.

## Known Limitations

- CDX can time out for extremely popular URLs even with `collapse=timestamp:8` — the timeout surfaces as `cdx_unavailable` after one request; a `from`/`to` range or a smaller `limit` keeps the query cheaper, and the resume key pages through the rest
- `ia_get_snapshot` text extraction drops scripts, styles, comments, markup, `<template>` content, and phrasing content its own `hidden` attribute or inline `display:none` hides; navigation, page chrome, and content hidden by a class, a stylesheet, or a hidden block element stay in the text. Only a link beside an element keeps a space between their words. Sibling elements that a stylesheet spaces apart with no link between them read joined: a price and its screen-reader copy, a location stamp and the headline after it. Agents needing raw HTML should use the replay URL directly
- Tables survive only as tabs and lines: a cell that opens with a block element loses its tab, nested tables flatten, and whitespace at the end of a `<pre>` line is dropped. A change to extraction can move `total_chars` and every `char_offset`, so a caller restarts a read at 0
- `include_links` lists only `<a href>` (no `<area>`, no script-built links, none inside a `<template>` or a hidden phrasing element), tracks one open anchor at a time (an `<a>` start tag closes the open one, even across table-cell boundaries), folds `<pre>` spacing inside a label to single spaces, and drops a capture link whose original has no scheme; links come from the first 4 MiB
- A page with no charset declaration that is not valid UTF-8 decodes with Wayback's guessed charset or windows-1252; a wrong guess can still substitute letters in a page that is neither UTF-8 nor windows-1252
- The CDX `sort=closest` fallback often takes longer than its 25 s ceiling for heavily archived URLs; closest mode then reports `cdx_unavailable` (`availability_unavailable` when the Availability API had failed first) and points at history mode
- `ia_get_snapshot` reads at most the first 4 MiB of a page
- Text and history cursors expire after one hour and depend on the configured state store; restarting an in-memory deployment invalidates its cursors. A changed text representation invalidates its text cursor. Offset paging and a fresh history query remain available
- Legacy CDX resume keys and wildcard history paging may omit the row at a page boundary (a wildcard page may return it as a later capture of the same URL); their responses disclose this limitation
- A `find` that matches nothing rules out one file from its start offset to its end only, and OCR misreads or line-end hyphens can hide a phrase. A match that begins inside a returned page and runs past its end is not reported by the next `find` search from that page's `next_continuation`. A deep `char_offset` on a slow link can fail as `archive_unavailable` before its search gets past it, and a search resumed by `char_offset` reads the file from its first byte again, so on a link too slow to pass the resume point within the request timeout only a continuation moves it forward
- `ia_get_text` reports no total character count — a document's length is known only once a page reaches its end (`has_more: false`); `source_file_bytes` gives the file's size in bytes, and UTF-8 text other than ASCII takes more than one byte per character
- Items in restricted collections return metadata, flagged `access_restricted`, but whether a download is refused is per file: `ia_get_item` marks a file the manifest lists as private with `private: true`, and `ia_get_text` surfaces a refused download (a 401 or 403) as `download_forbidden` rather than failing silently
- Copyright varies widely by item; the `licenseurl` and rights fields are surfaced as-is without legal interpretation
- The Advanced Search Solr index has a lag — very recently uploaded items may not appear

## API Reference

### Wayback Availability
```
GET https://archive.org/wayback/available?url={url}&timestamp={1–14 digits}   (timestamp omitted for the latest capture)
Response: { url, archived_snapshots: { closest?: { url, timestamp, status, available } }, timestamp }
  (closest.url uses http://web.archive.org — the service upgrades it to https)
Not-found: archived_snapshots = {} (HTTP 200) — also returned for some URLs that have captures
Error: HTTP 200 { error: { code, message } } with no capture, e.g. {"error":{"code":"timeout","message":"client timeout at 5.0 seconds"}} when its own lookup times out; a blank timestamp= draws HTTP 500
```

### Wayback CDX
```
GET https://web.archive.org/cdx/search/cdx?url={url}&output=json
  &fl=timestamp,statuscode,mimetype,original,digest,length   (field selection)
  &collapse=timestamp:8                                       (one per day; also digest, urlkey)
  &from={1–14 digits}&to={1–14 digits}                        (date range, normalized from the caller's forms)
  &filter=statuscode:200                                      (status filter)
  &limit=100                                                  (cap)
  &showResumeKey=true                                         (pagination token)
  &resumeKey={key}                                            (continue from)
  &closest={timestamp}&sort=closest                           (nearest captures first)
Response: array-of-arrays; row[0] = header; row[N] = data; trailing [] or [""] followed by [resumeKey] when more exist
Error: empty array or HTTP 503/504 on missing url param or overloaded query
```

### Advanced Search
```
GET https://archive.org/advancedsearch.php?q={solr_query}&output=json
  &fl[]=identifier&fl[]=title&fl[]=creator&fl[]=mediatype&fl[]=date&fl[]=publicdate&fl[]=downloads&fl[]=collection
  &rows=50&page=1&sort[]=downloads+desc&sort[]=identifier+asc
Response: { responseHeader: { status, QTime }, response: { numFound, start, docs: [...] } }
Error: HTTP 200 {"error": "…"} with no response on a rejected request; HTML page on empty q= or auth error
```

### Metadata API
```
GET https://archive.org/metadata/{identifier}
Response: { metadata: {...}, files: [{name, format, size, md5, ...}], ... }
Not-found: {} (HTTP 200)

GET https://archive.org/metadata/{identifier}/files
Response: { result: [{name, format, size, md5, ...}] }
Unknown or dark: {"error": "…"} (HTTP 200)
```
